# v0.2.0 release plan

Status: in development, based on `main` at `99dfff5`. No release date or tag is
scheduled. This plan covers the 13 open issues reviewed on October 21, 2026.

The release should improve generated workflows' handling of real commands,
filesystem effects, and completion evidence. Compiler behavior must remain
independent of a skill's name, wording, domain, and provider. A passing stub
run establishes mechanics only; it does not establish answer quality.

## Scope and sequence

Every issue below remains open until its requested behavior is implemented and
verified. The rollout tracker [#17](https://github.com/trailofbits/calcifier/issues/17)
coordinates owner feedback; it is not an additional compiler feature.

The first increment implements #8 and #19. The next increment provides configured
worker capabilities and call requirements for #7, including repair after a full
dry-run mismatch. For #11, the installed command contract explains implicit build
effects, opt-in and caller-provided isolation; neutral regressions cover hard
dry-run suppression and the permitted manual route. This does not establish the
quality of new real-provider generations or create a process sandbox.

The next increment addresses #9 through file gathering in `prepare_context`,
validating all selected source and manifest paths against resolved authorized
roots before any reads. For #10, `ensure_directory` can preflight the full
subprocess output set and excluded roots before creating the directory. Neutral
compiler/runtime regressions cover internal and escaping symlinks, complete
LF/CRLF content, pinned resources, intermediate collisions, project-contained
outputs, explicit replacement policy, and clean subprocess writes. These helpers
do not constrain arbitrary trusted Python or external processes; generated
recipes must use them with the workflow's complete input and output sets.

Rows 3 and 4 remain planned work. Each issue needs a concrete mechanism,
neutral regression, and review of its evidence limits before closure. Changes
to a prompt or runtime alone do not prove generated-recipe correctness.

## Verification and release gates

- Run focused offline regressions for each increment, then `gmake verify`.
  Tests use stub providers and never invoke live Claude or Codex. Do not run
  mutation testing locally.
- Always attempt the complete compiler dry run with synthesized inputs and
  stub agents. Preserve time/call limits and distinguish `passed`, `failed`,
  and `unverified` coverage.
- Keep generated evidence outside Git. Preserve the owner's checkout and use
  ordinary pushes from the isolated `release/v0.2.0` worktree.
- Owners run representative live acceptance after fixes in an appropriate
  isolated environment. Do not inspect held-out fixtures, cohort lists, or
  results. Offline checks cannot substitute for owner acceptance.
- Before release, reconcile this scope with unresolved issues, finish the
  changelog with the actual release date, check every version surface, build
  and verify the distribution artifacts, and follow the existing signed-tag
  publishing workflow. Creating this branch does not publish a release.
